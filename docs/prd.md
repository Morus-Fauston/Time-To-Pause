# PRD: 「停一下吧 (Time To Pause)」

> 版本: 1.0 | 日期: 2026-06-23 | 状态: Draft

---

## Problem Statement

短视频 App 的设计本质上是注意力经济——无限滚动、个性化推荐、自动连播，这些机制让用户"无意识下滑"，一刷就是几十分钟。现有防沉迷方案要么是**暴力锁死**（到时间直接封禁，引起逆反心理），要么是**形同虚设**（系统自带的使用时长统计藏在设置深处，几乎没人看）。

用户需要的是：**在"不知不觉刷了很久"和"彻底不让刷"之间，有一个中间地带**——一个能让他们在刷短视频时保持觉察、在被干预时仍保留选择权的工具。

## Solution

「停一下吧」是一个温和的手机防沉迷工具。它引入了一个**短视频额度**的概念：额度为 100 点，刷短视频时消耗，不刷时自动恢复。额度归零时，一个漂白蒙层会覆盖屏幕，让短视频画面变得"不好看"，同时提供算术题验证的宽限通道。

核心体验是**非对抗性劝导**——不是锁死你，而是让刷视频变得"没那么爽了"。想继续刷？可以，但需要答一道算术题来换 5 分钟缓冲。这个过程制造了一个"停顿"，让用户有机会从无意识下滑中抽离出来，主动问自己一句："我真的还想继续看吗？"

## User Stories

1. 作为一个每天刷抖音通勤的用户，我想在刷视频时看到额度实时减少，以便了解自己已经刷了多久。
2. 作为一个有自控意愿的用户，我想在停止刷短视频时看到额度自动恢复，以便知道自己"回血"了多少。
3. 作为一个短视频重度用户，我想在额度耗尽时看到一个醒目的视觉提示，以便被温和地打断而不是被暴力封禁。
4. 作为一个不想被完全锁死的用户，我想通过答题验证来获得 5 分钟宽限，以便在被干预时仍有继续观看的选择权。
5. 作为一个做错算术题的用户，我想可以无限重试换题，以便不会因为一次失误而被惩罚。
6. 作为一个在非短视频 App 中使用的用户，我想悬浮球自动隐藏，以便不被打扰。
7. 作为一个在 B 站看长视频的用户，我想我的额度不会因为看长视频而消耗，以便不误伤正常使用。
8. 作为一个刚安装的用户，我想看到一个温和的欢迎页介绍产品理念，以便理解这个工具是做什么的。
9. 作为一个刚安装的用户，我想逐步被引导开启权限，以便不会被一上来三个权限吓跑。
10. 作为一个担心后台耗电的用户，我想知道这个 App 对电量的影响很小，以便放心让它常驻运行。
11. 作为一个手机重启后的用户，我想 App 能自动恢复运行（如果我在设置中开启了此选项），以便不需要每次手动启动。
12. 作为一个希望保护隐私的用户，我想所有数据都存储在本地，以便不用担心短视频观看记录被上传。
13. 作为一个在宽限期的用户，我想看到通知栏的倒计时，以便随时了解还剩多少缓冲时间。
14. 作为一个人性化的用户，我想在宽限期间看到额度正常恢复，以便宽限结束后可能不需要立即再次被干预。
15. 作为一个从非短视频切换到短视频的用户，我想如果额度已经归零，蒙层会立即出现，以便不会"漏刷"。
16. 作为一个想了解产品价值的用户，我想在欢迎页看到模拟进度条动效和功能介绍，以便快速理解核心机制。
17. 作为一个喜欢视觉自定义的用户，我希望蒙层有不同模式可切换（漂白/渐变呼吸），以便选择自己喜欢的风格。
18. 作为一个手机被杀后台的用户，我希望重新打开 App 时额度已经按恢复速率补回，以便不会因为被系统杀死而损失额度。

## Implementation Decisions

### 模块结构

项目按职责划分为以下模块，对应 `com.ttp.pause` 包下的子包：

- **detector**（`AppDetector`）— 前台应用检测。使用 `UsageStatsManager` 按包名匹配白名单。纯短视频 App 仅匹配包名；B 站等复合 App 需要包名 + Activity 名称双重校验。Activity 名称通过 `AccessibilityService` 获取（备选方案），v1.0 内置已知 Activity 名列表。
- **data**（`QuotaStore`）— 额度持久化。使用 `SharedPreferences` 存储 4 个字段：`quota`（0-100）、`grace_end_timestamp`（宽限结束时间戳）、`last_tick_time`（最后更新时刻）。数据量极小（仅 4 个 key-value），无需 DataStore。
- **service**（`QuotaService`）— 后台核心驱动力。`ForegroundService` 内 `Handler.postDelayed(60s)` 循环，每分钟 tick 一次。每次 tick 执行：检测前台 App → 按时段（白天/夜间）计算消耗或恢复 → 更新 `QuotaStore` → 更新通知栏 → 若额度归零则触发干预信号。
- **receiver**（`BootReceiver`）— 开机自启。通过 `PackageManager.setComponentEnabledSetting` 动态启用/禁用（默认关闭），用户可在初始化引导中选择开启。

### 架构决策

- **后台 tick 采用 ForegroundService + Handler，不用 WorkManager**。WorkManager 最小间隔 15 分钟，不满足每分钟更新需求。Service 内 Handler 是进程内轻量定时器，无跨进程调用、不唤醒 CPU，国产 ROM 不受限。（参见 ADR-0001）
- **全量使用 XML + View 体系，不用 Jetpack Compose**。VS Code 对 Compose 无实时预览；悬浮球和蒙层需要 `WindowManager` 直接操作 View 层级，Compose 在此场景下不受支持。（参见 ADR-0002）
- **检测采用包名白名单 + Activity 名称，不用内容分析**。不上传任何用户数据，所有检测在本地完成。微信视频号、浏览器网页版等非主流入口暂不检测。（参见 ADR-0003）
- **UI 技术栈**：XML + AppCompat + ConstraintLayout + WindowManager（悬浮球/蒙层）。

### 核心状态机

```
                  ┌─────────────┐
                  │  正常运行态  │
                  │ (消耗/恢复)  │
                  └──────┬──────┘
                         │ 额度归零 + 短视频在前台
                         ▼
                  ┌─────────────┐
                  │  干预蒙层态  │
                  │  (漂白覆盖)  │
                  └──────┬──────┘
                         │ 点击"申请宽限" → 答对题
                         ▼
                  ┌─────────────┐
                  │  宽限状态    │
                  │ (5分钟倒计时) │
                  └──────┬──────┘
                         │ 倒计时结束
                         │
            ┌────────────┴────────────┐
            │                         │
            ▼                         ▼
    ┌──────────────┐         ┌──────────────┐
    │ 额度仍为0 →   │         │ 额度>0 →     │
    │ 回到干预蒙层   │         │ 回到正常运行  │
    └──────────────┘         └──────────────┘
```

### 关键约束

- 宽限期间**不可叠加**——宽限中悬浮球隐藏，通知栏显示倒计时
- 非短视频 App 在前台时，额度为 0 也不显示蒙层
- 被系统杀死后回溯恢复**仅恢复不消耗**（因无法知道被杀期间用户行为），加载 `last_tick_time` 模拟恢复至多到 100

## Testing Decisions

一个好的测试只验证外部行为，不验证实现细节。具体来说，应该测试"给定输入 X，输出是否为 Y"，而不是测试"内部状态 Z 是否被设置为特定值"。

### 测试策略层级

| 层级 | 目标 | 框架 | 职责 |
| :--- | :--- | :--- | :--- |
| 单元测试 | `QuotaEngine`（待抽取） | JUnit 5 | 额度计算逻辑、白天/夜间判定、回溯恢复、宽限状态转换 |
| 单元测试 | `AppDetector` | JUnit 5 + Mockito | 包名匹配、B站 Activity 判定、白名单变更 |
| 单元测试 | 算术验证 | JUnit 5 | 随机数范围、加减法正确性、结果 ≥ 0 |
| 集成测试 | `QuotaService.onTick()` | JUnit 5 + Mockito | mock QuotaStore + AppDetector，验证 tick 行为 |
| 手动测试 | UI 全流程 | 真机 | 权限引导、悬浮球交互、蒙层显示/隐藏、宽限答题 |

### 核心可测试性重构建议

当前 `QuotaService` 将业务逻辑与 Android 框架紧耦合。建议将以下逻辑抽取为纯 Kotlin 类 `QuotaEngine`：

```
QuotaEngine
├── fun calculateDelta(isWatching: Boolean, currentTime: Long): Int
├── fun catchUpRecovery(lastTickTime: Long, now: Long): Int
├── fun isDayTime(time: Long): Boolean
├── fun isGraceOver(graceEndTimestamp: Long): Boolean
└── fun generateArithmeticProblem(): Pair<String, Int>
```

此类无 Android 依赖，可直接 JUnit 测试。`QuotaService` 持有 `QuotaEngine` 实例，仅做胶水代码。

### 测试用例示例

```
QuotaEngineTest
├── testConsumeDay()     // 白天看视频 → -10
├── testConsumeNight()   // 夜间看视频 → -16
├── testRecoverDay()     // 白天不看 → +5

```

## Out of Scope

- **微信视频号、浏览器网页版短视频等非主流入口的检测**。技术成本高（需识别子页面/WebView），且与"专注纯短视频 App"的产品定位一致。留作未来扩展。
- **系统级颜色反转**。`ACCESSIBILITY_DISPLAY_INVERSION_ENABLED` 是系统级开关，开启后全局反转（短信、设置等全被反转），不可接受。采用悬浮蒙层漂白方案替代。
- **OCR/深度学习/截图分析**。违反隐私"零上传"原则和性能"CPU < 3%"要求。
- **iOS 版本**。本 PRD 仅覆盖 Android 平台。
- **多语言支持**。v1.0 仅支持中文界面。
- **数据统计仪表盘**。v1.0 不提供历史数据图表、使用趋势分析等功能。
- **社交/排行榜功能**。不与好友比拼、不设排名。

## Further Notes

### 关于"非对抗性"的边界

本项目有意选择了"温和干预"而非"强制封锁"的路线。这意味着**用户始终可以绕过限制**——宽限答题理论上可以无限循环。这是故意的：产品的目标不是"让用户刷不了"，而是"让用户在被干预时停顿一下，主动选择是否要继续"。这个设计哲学贯穿了所有决策。

### 白名单维护

B 站的 Activity 名称随 App 版本更新可能变化。建议在 v1.1 引入远程配置机制（如 Firebase Remote Config 或自建简单 JSON API），使白名单可以热更新而不需要发版。但 v1.0 采用硬编码内置列表。

### 成功指标参考

| 指标 | 目标值 | 衡量方式 |
| :--- | :--- | :--- |
| 干预触发频率 | 2-5 次/天 | 本地日志统计 |
| 宽限使用率 | < 80% | 答题次数 / 干预次数 |
| 7 日留存 | > 60% | 安装 7 天后未卸载 |
| 日均后台 CPU | < 3% | Profiler 测量 |
| 日均耗电 | < 2% | 系统电池统计 |

# PRD: 「停一下吧 (Time To Pause)」

> 版本: 1.7 | 日期: 2026-06-25 | 状态: Draft

---

## Problem Statement

短视频 App 的设计本质上是注意力经济——无限滚动、个性化推荐、自动连播，这些机制让用户"无意识下滑"，一刷就是几十分钟。现有防沉迷方案要么是**暴力锁死**（到时间直接封禁，引起逆反心理），要么是**形同虚设**（系统自带的使用时长统计藏在设置深处，几乎没人看）。

用户需要的是：**在"不知不觉刷了很久"和"彻底不让刷"之间，有一个中间地带**——一个能让他们在刷短视频时保持觉察、在被干预时仍保留选择权的工具。

## Solution

「停一下吧」是一个温和的手机防沉迷工具。它引入了一个**短视频额度**的概念：额度为 100 点，刷短视频时消耗，不刷时自动恢复。额度归零时，一个漂白蒙层会覆盖屏幕，让短视频画面变得"不好看"，同时提供算术题验证的宽限通道。

核心体验是**非对抗性劝导**——不是锁死你，而是让刷视频变得"没那么爽了"。想继续刷？可以，但需要答一道算术题来换 5 分钟缓冲。这个过程制造了一个"停顿"，让用户有机会从无意识下滑中抽离出来，主动问自己一句："我真的还想继续看吗？"

### 核心机制

- **额度**：0-100 点。刷短视频消耗，停止恢复。**无每日重置**，完全靠自然行为调节。
- **宽限**：答题换 5 分钟。宽限期间**额度完全冻结**——不消耗也不恢复，仅暂停干预。
- **悬浮球**：默认始终显示（可在设置中关闭：仅在看短视频时显示）。宽限期间切换为倒计时模式（剩余秒数 + 外圈进度环递减）。
- **蒙层**：非对抗性视觉干预。可选两种方向——**温和干预**（渐变呼吸动画，强调自我觉察）或**视觉剥夺**（漂白+背景模糊+动态噪点，各三档强度）。不拦截下层触控。
- **检测（v0.2.4.revised.3+）**：**A11y 优先，轮询兜底**。当 AccessibilityService 有效连接且 LastPkg 为短视频时，跳过轮询直接判定"在看"。轮询仅在 A11y 断开或包名非短视频时作为兜底。MIUI 设备上三个特有问题的修复详见 ADR-0005。方向优先——宁可多消耗不可错误恢复。

## User Stories

### 额度感知
1. 作为一个每天刷抖音通勤的用户，我想在刷视频时看到额度实时减少，以便了解自己已经刷了多久。
2. 作为一个有自控意愿的用户，我想在停止刷短视频时看到额度自动恢复，以便知道自己"回血"了多少。
3. 作为一个在意时间流逝的用户，我想悬浮球始终显示在屏幕上（不限于刷短视频时），并且环形进度条持续平滑动画，以便像时钟一样随时感知额度变化。
4. 作为一个在 B 站看长视频的用户，我想我的额度不会因为长视频而消耗，以便不误伤正常使用。

### 干预与宽限
5. 作为一个短视频重度用户，我想在额度耗尽时看到一个醒目的视觉提示，以便被温和地打断而不是被暴力封禁。
6. 作为一个不想被完全锁死的用户，我想通过答题验证来获得 5 分钟宽限，以便在被干预时仍有继续观看的选择权。
7. 作为一个做错算术题的用户，我想可以无限重试换题，以便不会因为一次失误而被惩罚。
8. 作为一个被蒙层打断的用户，我想蒙层不拦截下层触控、颜色偏浅、且有"返回"按钮可主动关闭，以便紧急情况下仍能正常操作手机。
9. 作为一个宽限期用户，我想额度完全冻结（不扣不加），以便宽限期单纯是"不被干预的时间"，而不是"回血时间"。
10. 作为一个宽限期的用户，我想看到通知栏的倒计时，以便随时了解还剩多少缓冲时间。
11. 作为一个从非短视频切换回短视频的用户，我想如果额度已经归零，蒙层会立即出现，以便不会"漏刷"。
12. 作为一个宽限算术对话框的用户，我想对话框上有"关闭"按钮可以退出，以便临时不想答题时可以离开。

### 首次体验
13. 作为一个刚安装的用户，我想看到一个温和的欢迎页介绍产品理念，以便理解这个工具是做什么的。
14. 作为一个刚安装的用户，我想逐步被引导开启权限，以便不会被一上来多个权限吓跑。
15. 作为一个想了解产品价值的用户，我想在欢迎页看到模拟进度条动效和功能介绍，以便快速理解核心机制。

### 主界面与设置
16. 作为一个完成初始设置的用户，我想启动 App 后进入主仪表盘而非退出应用，以便随时查看当前额度和状态。
17. 作为一个想调整设置的用户，我想在仪表盘上通过点击设置图标弹出设置菜单，以便进行权限重引导、进入调试模式或关闭应用。
18. 作为一个开发/高级用户，我想在设置中进入调试模式，以便手动调节额度用于测试。

### 后台与隐私
19. 作为一个担心后台耗电的用户，我想知道这个 App 对电量的影响很小，以便放心让它常驻运行。
20. 作为一个手机重启后的用户，我想 App 能自动恢复运行（如果我在设置中开启了此选项），以便不需要每次手动启动。
21. 作为一个希望保护隐私的用户，我想所有数据都存储在本地，以便不用担心短视频观看记录被上传。
22. 作为一个手机被杀后台的用户，我希望重新打开 App 时额度已经按恢复速率补回，以便不会因为被系统杀死而损失额度。

### 视觉与交互
23. 作为一个喜欢视觉自定义的用户，我希望蒙层有不同模式可切换（漂白/渐变呼吸），以便选择自己喜欢的风格。
24. 作为一个手机上有多种短视频 App 的用户，我希望检测覆盖抖音、快手、TikTok、微视等主流平台，以便所有平台都能统一管理。
25. 作为一个宽限期的用户，我希望悬浮球在宽限期间显示倒计时（外圈环形进度递减），以便直观感知剩余缓冲时间。
26. 作为一个不想被悬浮球一直打扰的用户，我可以在设置中选择"仅在看短视频时显示悬浮球"，以便桌面/其他 App 时不被干扰。
27. 作为一个被蒙层打断后仍想继续刷的用户，我希望关闭蒙层后有 30 秒防打扰期，30 秒后如果还在刷则蒙层重新出现，以便不被频繁打断但有节奏地提醒。
28. 作为一个喜欢视觉自定义的用户，我希望在设置中选择蒙层方向（温和的呼吸渐变 / 强力的视觉剥夺），以便符合个人偏好。
29. 作为一个想要临时停用服务的用户，我可以在通知栏点击"暂停服务"按钮，以便需要专注其他事情时不被额度提醒干扰。

## Implementation Decisions

### 模块结构

项目按职责划分为以下模块，对应 `com.ttp.pause` 包下的子包：

- **detector**（`AppDetector` + `ForegroundMonitorService`）— 前台应用检测。**v0.2.3+ 架构**：轮询为主、A11y 加速。`UsageStatsManager` 每秒查询是唯一的持续真相来源，连续 N=3 次一致才切换状态。`ForegroundMonitorService`（AccessibilityService）仅做瞬态跳转——短视频包名事件即时 WATCHING，已知非短视频 App 事件即时 LEAVING。系统弹窗和未知 App 事件完全忽略，不影响任何状态。包名判定通过 `AppDetector.isShortVideoApp()` 和 `isBilibili()` 完成，已知非短视频 App 白名单 `KNOWN_NON_VIDEO_PACKAGES` 包含 Launcher、社交、浏览器等 23 个包名。B 站通过 `BILIBILI_SHORT_VIDEO_ACTIVITIES` 白名单区分短视频/长视频。
- **data**（`QuotaStore`）— 额度持久化。使用 `SharedPreferences` 存储 3 个字段：`quota`（0-100）、`grace_end_timestamp`（宽限结束时间戳）、`last_tick_time`（最后更新时刻）。数据量极小（仅 3 个 key-value），无需 DataStore。
- **service**（`QuotaService`）— 后台核心驱动力。`ForegroundService` 内 `Handler.postDelayed(1s)` 循环（`secondRunnable`），每秒统一执行：检测前台 App（优先读 `ForegroundMonitorService.lastForegroundPackage`，降级读 `AppDetector`）→ 按每秒费率（Float）累加到 `_exactQuota` → 取整持久化 → 驱动 UI 更新。同时负责宽限计时、通知栏更新、回溯恢复。
- **receiver**（`BootReceiver`）— 开机自启。通过 `PackageManager.setComponentEnabledSetting` 动态启用/禁用（默认关闭），用户可在初始化引导中选择开启。

### 架构决策

- **后台 tick 采用 ForegroundService + Handler，不用 WorkManager**。WorkManager 最小间隔 15 分钟，不满足更新需求。Service 内 Handler 是进程内轻量定时器。（参见 ADR-0001）
- **全量使用 XML + View 体系，不用 Jetpack Compose**。VS Code 对 Compose 无实时预览；悬浮球和蒙层需要 `WindowManager` 直接操作 View 层级，Compose 在此场景下不受支持。（参见 ADR-0002）
- **检测采用 A11y 优先 + 轮询兜底架构（v0.2.4.revised.3+）**：A11y 有效连接且 LastPkg 为短视频时跳过轮询。轮询（UsageStatsManager, N=5 确认）仅在 A11y 断开或 LastPkg 非短视频时启用。系统弹窗和未知 App 事件完全忽略。方向优先——宁可多消耗不可错误恢复。MIUI 特有适配详见 ADR-0005 的 MIUI 兼容性备忘录。
- **UI 技术栈**：XML + AppCompat + ConstraintLayout + WindowManager（悬浮球/蒙层）。
- **检测与结算合一**：单个 `secondRunnable` 每秒同时做检测、计算、UI 更新。

### 检测架构演进（v0.2.0.revised → v0.2.4.revised.5）

v0.2.x 的核心工作是解决"一直在刷抖音但额度异常变化"的检测 bug。经历了 **4 个架构阶段、17 次迭代**，最终于 v0.2.4.revised.5 稳定。详见 CHANGELOG.md 的完整修复历程和老 ADR-0003 的完整演进史。

| 阶段 | 版本范围 | 核心原则 | 结果 |
|:----|:---------|:---------|:-----|
| L1 | v0.2.0.revised.1~11 | A11y 主 + 轮询备选 + keepalive 时间戳 | 三源冲突，系统弹窗穷举不尽 |

### 检测状态机（v0.2.4.revised.5+）

```
                  ┌─────────────┐
                  │  正常运行态  │
                  │ (消耗/恢复)  │
                  └──────┬──────┘
                         │ 额度归零 + 短视频在前台
                         ▼
                  ┌─────────────┐
                  │  干预蒙层态  │
                  │  (漂白覆盖)  │
                  └──────┬──────┘
                         │ 点击"申请宽限" → 答对题
                         ▼
                  ┌─────────────┐
                  │  宽限状态    │
                  │ (5分钟倒计时,  │
                  │  额度冻结)    │
                  └──────┬──────┘
                         │ 倒计时结束
                         │
            ┌────────────┴────────────┐
            │  (宽限冻结额度不变)      │
            ▼                         ▼
    ┌──────────────┐         ┌──────────────┐
    │ 额度仍为0 →   │         │ 额度>0 →     │
    │ 回到干预蒙层   │         │ 回到正常运行  │
    └──────────────┘         └──────────────┘
```

> 注：宽限期间额度冻结，因此"额度>0"的分支意味着用户在宽限开始前额度就大于 0（非零触发的宽限）。典型场景为零触发的宽限，结束后回到蒙层。

### 关键约束

- 宽限期间**不可叠加**——额度完全冻结，不消耗不恢复，通知栏显示倒计时
- 非短视频 App 在前台时，额度为 0 也不显示蒙层
- **秒级精确结算**：`QuotaService` 每秒执行，检测优先走 `ForegroundMonitorService`（事件驱动），备选走 `UsageStatsManager` 5 秒窗口确认前台 App。按每秒费率（±0.167/±0.083 等）累加到 `_exactQuota`（Float），取整写回。追赶动画 0.6 秒完成大幅变化。
- 被系统杀死后回溯恢复**仅恢复不消耗**（因无法知道被杀期间用户行为），加载 `last_tick_time` 模拟恢复至多到 100

## Testing Decisions

一个好的测试只验证外部行为，不验证实现细节。具体来说，应该测试"给定输入 X，输出是否为 Y"，而不是测试"内部状态 Z 是否被设置为特定值"。

### 测试策略（分阶段推进）

**阶段 A（v0.2.x revised）**：只测无 Android 依赖的纯逻辑层。
**阶段 B（v0.4.x）**：搭建完整 Android 测试框架（JUnit 5 + Mockito + Robolectric），覆盖所有模块。

### 阶段 A — `QuotaEngine` 纯逻辑测试

| 层级 | 目标 | 框架 | 职责 |
| :--- | :--- | :--- | :--- |
| 单元测试 | `QuotaEngine` | JUnit 5 | 额度计算逻辑、白天/夜间判定、回溯恢复、宽限状态转换 |
| 单元测试 | `AppDetector` + `ForegroundMonitorService` | JUnit 5 + Mockito | 包名匹配、B站 Activity 判定、白名单变更、前台切换事件处理 |
| 单元测试 | 算术验证 | JUnit 5 | 随机数范围、加减法正确性、结果 ≥ 0 |
| 集成测试 | `QuotaService.onTick()` + 事件结算 | JUnit 5 + Mockito | mock QuotaStore + AppDetector/MonitorService，验证 tick 行为和秒级结算 |
| 手动测试 | UI 全流程 | 真机 | 权限引导、悬浮球交互、蒙层显示/隐藏、宽限答题、无障碍服务开关验证 |

### 核心可测试性重构建议

当前 `QuotaService` 将业务逻辑与 Android 框架紧耦合。建议将以下逻辑抽取为纯 Kotlin 类 `QuotaEngine`：

```
QuotaEngine
├── fun calculateDelta(isWatching: Boolean, currentTime: Long): Int
├── fun catchUpRecovery(lastTickTime: Long, now: Long): Int
├── fun isDayTime(time: Long): Boolean
├── fun isGraceOver(graceEndTimestamp: Long): Boolean
└── fun generateArithmeticProblem(): Pair<String, Int>
```

此类无 Android 依赖，可直接 JUnit 测试。`QuotaService` 持有 `QuotaEngine` 实例，仅做胶水代码。

## Out of Scope

- **微信视频号、浏览器网页版短视频等非主流入口的检测**。技术成本高（需识别子页面/WebView），且与"专注纯短视频 App"的产品定位一致。留作未来扩展（v0.5.x+）。
- **系统级颜色反转**。`ACCESSIBILITY_DISPLAY_INVERSION_ENABLED` 是系统级开关，开启后全局反转（短信、设置等全被反转），不可接受。采用悬浮蒙层漂白方案替代。
- **OCR/深度学习/截图分析**。违反隐私"零上传"原则和性能"CPU < 3%"要求。
- **iOS 版本**。本 PRD 仅覆盖 Android 平台。
- **多语言支持**。v0.4.x 仅支持中文界面。
- **数据统计仪表盘**。v0.4.x 不提供历史数据图表、使用趋势分析等功能。
- **社交/排行榜功能**。不与好友比拼、不设排名。

## Further Notes

### 关于"非对抗性"的边界

本项目有意选择了"温和干预"而非"强制封锁"的路线。这意味着**用户始终可以绕过限制**——宽限答题理论上可以无限循环。这是故意的：产品的目标不是"让用户刷不了"，而是"让用户在被干预时停顿一下，主动选择是否要继续"。这个设计哲学贯穿了所有决策。

### 白名单维护

B 站的 Activity 名称随 App 版本更新可能变化。v0.3.x 引入 GitHub Raw JSON 远程配置机制，使 B 站 Activity 白名单可以热更新而不需要发版。
